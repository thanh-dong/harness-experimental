Implementation notes — US-028a Event-Log Shadow Mode

design decision Design decisions

DecisionRejected alternativeWhy
Emit events at the HarnessService (application) seam, after repository success. Emit inside each SqliteHarnessRepository method. Every CLI mutation already funnels through the service; repository-level unit tests stay event-free; infrastructure diff stays minimal. propose --commit covered via its returned committed proposals.
import brownfield emits no events. Synthesize events for imported rows. It is the legacy seed that migrate-to-events (US-028b) replaces with proper genesis events; shadow logs capture post-shadow mutations only. Emitting import events would double-count rows at migration time.
Add serde_json dependency. Hand-rolled JSON writer + parser. Rebuild must parse events; a hand-rolled parser is real risk surface for a correctness-critical replay path. Writer-side reuses the same crate.
Rebuild sets every timestamp from the event (recorded_at), never datetime('now'). Let schema defaults fill created_at. Defaults make two rebuilds differ by wall clock — determinism proof would be flaky by construction.
Writer id: FNV-1a 64 hash of email (8 hex) + 4-hex per-clone suffix in <gitdir>/harness-writer; HARNESS_WRITER overrides. SHA-256 of email; suffix in tracked file. Spec asks for a "hashed short form", not a cryptographic commitment; FNV keeps the crate dependency-free for hashing and is deterministic cross-machine. The suffix must be untracked (decision 0008 Q3) — the git dir is the natural untracked home and survives git clean.
Dump hash: FNV-1a 64 over canonically-serialized durable-8 rows. SipHash / DefaultHasher. RandomState is randomly keyed per process — a determinism proof hashed with it can never match across rebuild invocations.

deviation Deviations

None from the ratified frame. One from the parent spec's letter: ULID randomness uses RandomState-derived entropy (std-only) rather than a CSPRNG; uniqueness and per-process monotonicity are what replay ordering needs, and US-028b can revisit if cross-process same-millisecond ordering ever matters (DKR-4 showed cross-writer ties break on the writer field anyway).

tradeoff Tradeoffs & accepted limits

  • Shadow guarantee means a broken events dir silently degrades to warnings — accepted for US-028a because harness.db is still authoritative; US-028b flips this (event append becomes the write of record and must fail hard).
  • No watermark/incremental replay yet — rebuild is full replay only. DKR-2 measured full rebuild at 38.6 ms/10k events, fine for shadow-phase CI proof; the stat short-circuit watermark is designed into US-028b from the start.
  • story verify-all emits one story.verify_result event per verified story (not one batch event) — chattier, but mirrors the cutover op set one-to-one.
  • Rebuild runs with PRAGMA foreign_keys=OFF and update-type events that target rows with no genesis event (pre-shadow rows, e.g. a story.verify_result for US-028a itself) update zero rows silently. Both are inherent to a partial shadow log: the log's own integrity — not SQLite FK enforcement — is the replay contract, and migrate-to-events genesis (US-028b) closes the gap. The corrupt-line refusal test covers the failure mode that actually matters (malformed log).

open question Open questions

  • Should shadow logs be committed during the shadow phase, or only after cutover? Recommendation: keep them untracked until US-028b (add .harness/ to gitignore is not done — leave untracked-but-present so real dogfood data accumulates for the migration rehearsal); decide at US-028b intake.
