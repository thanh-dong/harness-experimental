# US-028b Design

Parent contract: `docs/stories/epics/E05-event-log-durable-layer/US-028-event-log-durable-layer.md`
(Design sections already carry the accepted DKR evidence). This file pins the
decisions the parent leaves open.

## Row identity (stage 1)

- Schema migration `007-ulid-ids.sql`: recreate `intake`, `backlog`, `trace`,
  `intervention`, `story_signal` with `id TEXT PRIMARY KEY`; existing integer
  ids survive as their decimal strings (`'1'`, `'2'`, …) — this is what lets
  DKR-3's `payload.id` preservation hold through genesis. FK columns
  (`trace.intake_id`, `intervention.trace_id`, `story_signal.trace_id`)
  become TEXT.
- New rows mint ULIDs app-side (same generator as event ids). Two writers can
  never collide: ids are ULIDs, files are per-writer.
- **Id input**: anywhere the CLI takes a row id (`--trace`, `--intake`,
  `backlog close --id`, `score-trace`, `score-context`) it resolves an
  unambiguous prefix; ambiguity is an error listing candidates; legacy
  numeric ids match exactly first.
- **Id display**: full ULIDs. Deviation from the parent's "prints short
  forms": a ULID's prefix is its timestamp, so any truncated display form is
  ambiguous exactly for burst-created rows and cannot be safely pasted back.
  Full display + prefix input keeps the `backlog close --id <x>` ergonomics
  honestly.

## Migration (stage 2) — the three DKR-3 clauses are binding

`harness-cli migrate-to-events`:

1. Refuse if the cache is already event-backed (idempotent no-op if the
   existing genesis file is byte-identical to what would be produced).
2. Read every durable-8 row → one genesis event per row: writer `migration`,
   op = the table's add op, `recorded_at` = original `created_at`,
   `payload.id` = original id, **deterministic event id** (ULID whose time
   part is the original `created_at` ms and whose random part is
   `fnv1a64(table || id)` — distinct from the live ULID path, so re-runs are
   byte-identical).
3. Prove before installing: rebuild a temp cache from the candidate genesis
   events; per-table row counts AND canonical content hashes must equal the
   live DB — `tool` compared **excluding `status` and `checked_at`**;
   `schema_version`/`sqlite_sequence` are cache artifacts, never compared,
   never logged.
4. Install: back up `harness.db` → `.harness/backup/harness.db.pre-migration`;
   archive any pre-cutover shadow log files →
   `.harness/backup/pre-migration-events/` (shadow logs were never source of
   truth and their content is already captured by genesis — leaving them in
   place would double-apply rows on replay); write
   `.harness/events/migration.jsonl`; mark the cache event-backed; write
   watermarks.

## Cutover write path (stage 3)

- `cache_meta` table (migration 007): `event_backed` flag +
  `event_watermark(file, consumed_count, file_size, file_mtime_ns, tail_hash)`.
- **Freshness check on every command** (reads and writes): stat each
  `.harness/events/*.jsonl`; size+mtime match watermark → proceed (DKR-2:
  0.004 ms). Size grew → hash-verify prefix cheaply via stored tail hash,
  incrementally apply new lines, update watermark. Size shrank or hash
  mismatch → full rebuild into the cache (log is truth). Missing
  `harness.db` entirely → full rebuild (fresh-clone contract).
- **Mutation** = validate against fresh cache → build event (ULID id minted
  here) → append to own writer file + fsync (**failure fails the command** —
  the US-028a shadow guarantee is explicitly flipped) → `apply_event` to the
  cache (the same function replay uses) → update own watermark.
- A DB with rows but no event backing refuses mutations with "run
  harness-cli migrate-to-events" (prevents silent drift for existing repos).
  `init` on a fresh repo starts event-backed from genesis (empty log).

## Causal audit (stage 4) — DKR-4 binding clarification

- Each event gains an optional `observed` field: `{writer: consumed_count}`
  snapshot at append time (the writer's own watermark view).
- During apply (replay and live), a per-`(story, field)` last-update record
  is kept in the cache (`field_last_update`). An incoming cross-writer update
  to the same field is **concurrent** iff its `observed[last.writer]` count
  does not cover the last update's position in that writer's file. Concurrent
  → row in `lww_audit` (loser id, winner id, story, field) — deterministic,
  rebuilt from the log like everything else.
- Surfaced via `harness-cli audit` (new category) — wall-clock windows are
  rejected by design; a time bound may throttle display only.

## Generated views (stage 5)

- `docs/TEST_MATRIX.md` and `docs/HARNESS_BACKLOG.md` regenerated from the
  cache after any mutation of their tables, headed by
  `<!-- generated by harness-cli — do not hand-edit -->`.
- Guard at migration time: rows present in the markdown but absent from the
  DB (never imported) are reported and require `import brownfield` (its final
  act as a seed tool) before the view generation overwrites them.
- Views regenerate only when content changes (idempotent output, stable
  ordering) so PR diffs stay meaningful — this is the `pr_reviewability`
  wall's read surface.

## Two-writer proof (stage 6)

Rust integration test driving real `git`: init bare origin, two clones, each
clone mutates through the event-backed path with different `HARNESS_WRITER`s,
push/merge branches, assert zero merge conflicts, rebuild on the merge result
contains every record from both writers. This is the
`merge_conflict_count == 0` anti-goal read from the frame.
