The work came from a /claude-api prompt-audit run on 2026-09-07 that found 31 problems in the harness's model-facing text (12 high, 11 medium, 8 flag-only). It ran as eight tasks on the branch chore/prompt-audit-remediation, each its own commit with an independent review round. The task plan is in plan.md next to this file.

design decision Design decisions

The contract file wins over skill prose, and a lint enforces it

The OKR skill kept its definition of a complete artifact in two places: the machine-readable contracts/handoff-contract.v*.json and the human prose in SKILL.md. They had drifted, so the verifier failed on a real artifact that obeyed the skill. The rule we settled on is that the contract file is the single source of truth, the skill prose must carry the contract's exact sentences, and scripts/lint-skills.sh fails when the prose stops carrying them. That turns "the skill and the checker agree" from a hand check into a build check.

Two extra rows in CONTEXT_RULES.md, so the installer's claim is true

The one Harness reading block now shared by AGENTS.md and both installers says the lane-dependent docs are prescribed by docs/CONTEXT_RULES.md, and it names docs/TOOL_REGISTRY.md and docs/GOAL_LOOP.md. Neither document appeared in docs/CONTEXT_RULES.md. Two ways out: shorten the reading block, or make CONTEXT_RULES.md match it. We added the two rows, because the reading block is the text three files must agree on and the lane table is the place a reader looks up "what do I read in this lane".

Variant B adopted: the story's criterion is verifier completeness

Task 6 A/B-tested two versions of SKILL.md by giving each to a blind Fable writer and scoring the artifact with the verifier. The brief's written rule was a conjunction — adopt B only if it satisfies every requirement A does and is not longer — and the literal reading returned "keep A" on a 29-word artifact difference. The controller overrode it and adopted B. The reason: B is a strict superset on completeness (18/19 against 16/19), and a 0.55% gap between two artifacts written independently by two agents is writer noise, not a measured verbosity cost. The length clause was meant to catch over-elaboration, which did not happen.

Keep the deterministic verification steps under Fable 5.1

A stronger model is a reason to trust a plan more, not a reason to stop checking the result. The verification scaffolding (lints, story verify, the independent check on high-risk work) stays as written; recorded as docs/decisions/0013-keep-verification-steps.md.

deviation Deviations

Lane ruled normal, not high-risk

Three risk flags and no hard gate. The installer shim wording was treated as existing behavior rather than a public contract, which kept the story in the normal lane. If that call was wrong, the work should have had a human design review. It was mitigated by an agent review of D3 and a review round on every task commit.

The fixture was revised once, after the skill changed

The fixture was written first, on purpose, against the pre-change skill, so the baseline run would fail honestly (16 of 20). The skill then renamed three governance fields. The fixture was revised exactly once, limited to those three names, so it kept describing the same artifact under the new vocabulary rather than being tuned to pass.

Wording changes outside the literal brief

  • learning-memory.md: "scored blindbox eval" was reworded. It was grader vocabulary leaking into shipped instructions, which is exactly what the new lint assertion 3 forbids, but the file was not in the task's declared file list.
  • Task 3's regex for the generated-view check makes the leading backtick optional. The brief's regex text and its own forced-failure string contradicted each other; the optional backtick satisfies both.
  • Task 7 changed a stale "8/8" in CLAUDE.md to "a full score", because the score became 10/10 in this same story. Task 8 fixed the matching "8/8" in the story's own Validation table for the same reason.
  • Task 4 fixed two PHASE2.md mentions the brief did not name, because leaving them would have failed the brief's own verification grep.

What was deliberately not changed

Controller-owned planning artifacts (plan.md, the task briefs) still quote the old strings PHASE2.md and handoff-contract.v1.json, because they describe what the work was told to do. CHANGELOG.md keeps handoff-contract.v1.json in the July 2026 entry, which is a correct historical record.

open question Open questions

  1. Should artifact length ever be a decision criterion? It decided nothing here — a 0.55% gap was ruled noise — but the rule as written would have kept the worse variant. Recommendation: drop raw artifact length from the adopt/reject rule and keep skill-text length as a separate, reported number. If a length guard is wanted, make it a threshold wide enough to mean something, for example 10%.
  2. Does the parallel-launch sentence in CLAUDE.md stay? It restates what Claude Code's own tool prompt already says, so for Claude it is one wasted clause. Codex reads the same file and gets no such prompt. Recommendation: keep it. One clause is cheap, and the file is shared by two runtimes.
  3. Should the per-PKR allowed/forbidden action lists come back? Variant B narrowed them to the frame level and the verifier did not object. Recommendation: leave them out for now and re-check on the next real OKR run. If a worker acts outside its envelope in practice, that is the signal to restore them per PKR.
  4. Where do the seven deleted self-review rules live? coherence_review and coherence_review_source were removed from the contract; the verifier never read them. Every rule is still enforced by a requirement, but the written rules themselves are gone. Recommendation: no action; reopen only if a future artifact fails in a way the requirements do not explain.
  5. Should dkr_to_dkr_worked be reworded? Both A/B artifacts missed it, so neither variant's prose makes that phrasing reliable. Recommendation: treat it as a skill gap and fix the wording in a follow-up, not as a verifier bug.

Final whole-branch review and fix wave

A Fable reviewer read the whole branch (afda1a2..c508f05) against the story. It found two Important items the per-task reviews could not see: docs/SETUP.md still said "expect 8/8", and the MCP flavor docs/templates/mcp/session-context.md still carried the old seven-document reading list while the bash flavor had moved to "FEATURE_INTAKE.md plus query matrix, then CONTEXT_RULES.md per lane". One fix wave (commits 4cfb0c9 and ee0d36b) addressed those plus: the CLAUDE.md lane-dependent list no longer names CONTEXT_RULES.md (and the installer's CLAUDE shim copy was edited to match); README.md and SETUP.md reading pointers unified; HARNESS.md done definition names proof flags instead of matrix entries; the OKR skill's Output section now points at ## Contract, Step 2b regained the loop-termination sentence in prose, the dkr_to_dkr_worked line lists the six token groups verbatim, and contract source strings cite the Contract section; HARNESS_COMPONENTS.md says "independent review"; US-027's notes cite US-024 instead of PHASE5.md. Ruling: no numeric check count anywhere in prose ("expect a full score"), so the number cannot go stale again. Scoped re-review: all eight findings addressed. Final state: verify-harness 10/10, test-install-contract 22/22, lint-skills and lint-mcp-templates clean, check-diagrams 11 ok, fixture 19/19, story verify pass, entropy score 3/100.

Two pre-existing issues surfaced by the reviews were recorded as backlog items rather than fixed: the installer manifest does not ship the new lint scripts or the skill trees, and the intake-griller skill keeps its own seven-item source list.
