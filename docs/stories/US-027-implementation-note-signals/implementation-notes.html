Implementation notes — US-027 Implementation note signals

This note is itself the dogfood: it is the first implementation-notes.html written under the convention this story shipped (Move 1), and its categories below are the exact signal types propose now mines (Move 2).

design decision Design decisions

DecisionWhy
Keep propose rule-based; record signals at write time instead of parsing HTML. The engine's value is auditability. Parsing free-form HTML would make proposals non-deterministic — the failure mode docs/stories/US-024-improvement-proposal-pipeline.md calls out. So the agent emits a typed story_signal row; the engine only counts.
New story_signal table, not a reused one. intervention is an external correction; harness_friction is per-run. A signal is the agent's own design narrative, typed by the four note headings. Overloading either would blur both propose loops.
Mirror the intervention command path across all four layers. Lowest-surprise integration: same add/query shape, same repeated_values grouping, same confidence_for_count rule, same >= 2 threshold. No new concepts in the engine.

deviation Deviations

PlannedActualWhy
Add migration 006 and run tests. Also had to edit three hardcoded schema_version assertions (init_creates_database_and_schema, the migrate test, and the 005 backfill test). Those tests assert the latest schema version literally (== 5, vec![2,3,4,5], vec![5]), so every new migration breaks them. Fixed to 6 / vec![..,6] / vec![5,6]. This is a recurring harness friction — recorded as a deviation story signal, and propose already surfaced it as a "Task specification" proposal (proof below). The self-evolution loop caught its own tax.

tradeoff Tradeoffs & accepted limits

ItemNote
Recording is partly manual The agent decides which note categories are recurring enough to record as a signal. Accepted: mechanical "log every heading" would bury the mineable signal in noise. The HTML stays the full narrative; the row is the subset.
story_id keeps the REFERENCES story(id) FK Stricter than intervention.story_id (which has no FK). It rejected a reference to a non-existent story during the live demo — correct behavior. Cross-story recurrence is still expressible via unlinked (NULL story) signals, which propose groups purely by (type, summary).
Component is fixed to Task specification A recurring signal almost always implicates the spec/plan/template. Per-type or agent-supplied component mapping is deferred (decision 0007 follow-up).

open question Open questions

QuestionRecommendation
Should the recurring schema_version assertion friction be fixed now (e.g. assert >= N or derive from the migration list)? Out of scope for US-027 — but it is exactly the kind of gap this story is meant to surface. Recorded as a backlog item via the signal; let it accumulate one more occurrence before changing the test pattern, per the validation plan.
Should component be agent-supplied per signal rather than fixed? Defer until a few real stories show whether the fixed attribution misleads. Tracked in decision 0007 Follow-Up.
